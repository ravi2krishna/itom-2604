Class - 5
===========

    -> Configuration Items (CI's)

        -> A Configuration Item (CI) in servicenow is a digital Record 
        within the CMDB, representing "Any Manageable IT Component"
        such as Servers, Applications, Network Devices etc 

        -> CI's Track Infrastructure Details (Manufacturer, Vendor, Locations)
        to Support ITIL Process 

        -> Any Configuration Item Has Three Things 

            -> Class (What Type Of Asset Is It)

                -> Windows Computer 

                -> Linux Server 

                -> Application 

                -> etc 

            
            -> Attributes (Properties Of Asset)

                -> Manufacturer 

                -> Operating System 

                -> CPU Type 

                -> Disk 

                -> RAM 

                -> etc 


            -> Relationships (Connection With Other Assets)

                -> A Relationship In ServiceNow is a Connection 
                between Multiple Configuration Items, which defines 

                    -> How They Interact With Others 

                    -> How They Depend On Others 

                    -> Few Examples Include 

                        -> Runs On (An Application Runs On Server)

                        -> Used By (Configuration File Is Used By Application)

                        -> Depends On (Business Service Depends On An Application)

                        -> Connected By (A Server Is Connected By Switch)

                
                -> NOTE: The Relationships are automatically Discoverd During 
                Service Discovery, and all the Discoverd Relationships are updated in CMDB 

            -> Manual: https://www.lansweeper.com/wp-content/uploads/2019/06/All-servers-by-type.png

    -> Credentials 

        -> Once MID Server Is Installed, it tries to reach the devices on the network 
        range defined, and in order to Communicate with them, we need Credentials.

        -> Credentials are Authentication Secrets Stored On Service Now PDI 

        -> Credentials are Stored in "discovery_credentials" table 

        -> MID Servers Encrypts The Credentials 

        -> We Have Different Types Of Credentials 

            -> Windows Credentials Uses Username & Password 

            -> SSH Credentials Uses In Unix & Linux Environments 

                -> SSH Credentials are Made Up Of Public & Private Keys(Key Pair)
                Typically Goes With Passwordless Authentication.

            -> JDBC  Credentials For Database Connectivity 

            -> Cloud Components Might Use API Keys or Tokens 

        -> NOTE: If Credentials Are Updated Incorrectly, We cannot perform Discovery.



    -> Probes & Sensors 

        -> Probes & Sensors Are Two Halves Of Same Job 

    
    -> Probes 

        -> A Probe Is A Question 

            -> It's Script / Command That MID Server Executes Against 
            Target Devices To Collect Raw Data 

            -> It Runs On MID Server Side, Reaches To Target Device and Brings Back 
            All The RAW Output Like Commands / XML / Windows Queries / JSON ect 

            -> The Raw Data Output Will Be Stored At ServiceNow Inside 
            ECC Queue (External Communication Channel)


        -> A Sensor Is An Answer 

            -> It's Script / Command That Takes Raw Output From Probes and 
            Pareses It, To Extract information like fields OS, IP, Hostname,
            Softwares Installed, Ports Used etc 

            -> After Parsing Maps Them To CI Attributes, thus Updating Records in CMDB 

        -> NOTE: 
            
            -> Probes Goes and ASKS

            -> Sensors Comes Back and ANSWERS 


    -> Detective Story 

        -> Detective Assistant / Probe 

            -> Goes To Crime Scene, Takes Photos, Lifts Fingerprints, Collects Items etc 
            (Collects All Raw Evidences)

            -> ITOM: Probes Runs Scripts and Collects Data 

        
        -> Bag Of Evidence / ECC Queue 

            -> This Bag Of Evidence Contains Full Of Unprocessed Raw Evidence Items 

            -> ITOM: RAW Data Collected (Unprocessed Data)

        
        -> Detective / Sensor 

            -> Detective Sits At Desk, Opens The Bag Of Evidence,
            Starts Examining Each Item and Extracts Meaning Of Those Items 
            and Writes Final Report 

            -> ITOM: Extract Data From ECC Queue and Gives Meaningful Fields 
            like OS, IP, Hostname, Softwares Installed, Ports Used etc 


    -> Complete Flow 

        -> ServiceNow Says - Go Discover This IP 

            -> MID Server Sends Probe (Runs Command/Script On Target Device)

                -> Data Drops Into ECC Queue 

                    -> Sensor Picks Up (Reads, Parses & Extracts)

                        -> CMDB Gets Updated With New CI Record / Updates Existing CI Record

                        
Class - 8
===========

    -> Patterns 

        -> Patterns are servicenow modern Replacement for Probes / Sensor Approach 
        For Applications and Software Services 

        -> Probes and Sensors are still heavily used for infrastructure
        (Hardware / Operating System / Network)

        -> NOTE: Patterns are preferred method for Discovering Applications & Services 

        -> A Pattern is an Declarative Definition Unlike Imperative Definition Of 
        Probes & Sensors, 

        -> Patterns Discover Software Types & Services 

            -> Defines: What To Look For, Which Command To Run, What Files To Read 

                -> Imperative Definition Means "How To Do" 

                -> Declarative Definition Means "What To Do"

        
        -> NOTE: Patterns are written in Pattern Designer / Visual Designer 
        rather than using Raw Javascript 

        -> A Pattern Has An Identification Section, which defines what this 
        pattern should run - for example if port 80 is there this is web server.



    -> Discovery Schedules 

        -> A Discovery Schedule Is the Configuration Record that defines a discovery run 

        -> Discovery Schedule Answers 

            -> What Should Be Scanned 

                -> IP Address - Single Device 

                -> IP Ranges - Multiple Devices 

                    -> 10.0.0.0/20 

                        -> Scan 4000+ Devices 

                    -> 10.0.0.0/24 

                        -> Scan 250+ Devices 

            
            -> When To Do Scan 

                -> Schedule Like Run Daily 

                -> Schedule Like Run Weekly 

                -> On Demand (whenever you want) 

            
            -> Which Mid Server To Use For Scanning 

                -> Datacenter - Mumbai - Ecommerce Infrastructure

                    -> mid_server_mumbai

                -> Datacenter - New york - Ecommerce Infrastructure

                    -> mid_server_new_york 

        -> NOTE: Key Fields Used For Discovery Schedule 

            -> IP Range 
            -> Schedule 
            -> Mid Server Name 

        -> NOTE: When Schedule Is Completed, It Creates "Discovery Status" Record 

        -> Discovery Log, within each Status Record Is Your "Debugging Tool" 

            -> It Shows Every Step 

                -> What IP Address Was Tried 

                -> What Probe Was Executed (Hardware)

                -> What Pattern Was Executed (Software)

                -> What Sensor Ran To Parse Data 

                -> What CI Was Created in CMDB

                -> What CI Was Updated in CMDB

                

Class - 9
===========

    -> CI Classification 

        -> CI Classification is the Final Step, where the "Classifier Engine" 
        which determines What CI Class To Create and Whether 

            -> To Create a new CI or 

            -> Update An Existing CI 

        -> When a Sensor or Pattern finished Parsing Data From Devices, they hand over 
        Raw Attributes To CI Classifier Engine

        -> The CI Classifiers Engine Job Is To Look At The Attributes and Answer 
        following Question 

            -> What Type Of CI is this ? 

            -> Does This Already Exist In CMDB ? 

        -> NOTE: Classifier Engine == Identification Rules 

    
    -> Identification / Reconciliation 

        -> Rules For Matching Configuration Item Before insert / update 

    
    
    -> IRE (Identification & Reconciliation Engine)

        -> IRE is underlying servicenow Engine which uses identifier Rules 

            -> Each Class Has Defined Set Of Identifier Fields which makes a CI Unique 

            -> Criterion attributes are like Unique Fingerprints For CI 

                -> For A Web Server Like Apache, the combination of 
                sys_class_name + config_file + version is the unique identifier 

                -> For A Docker Container, the container_id is the unique identifier 

                    -> A Docker container ID is a globally unique, automatically generated
                    alphanumeric string that serves as the primary identifier 
                    for an individual Docker container. It is a 64-character hexadecimal string.

                -> For A Tomcat Server, the sys_class_name + install_directory + running process
                is the unique identifier 

            
            -> NOTE: If IRE Finds a match, it updates the existing CI, 
            this is called Reconciliation. 

            -> NOTE: If IRE Doesn't Finds a match, it Creates New CI, 
            this is called Reconciliation. 


        -> Simple Analogy To Understand IDE 

            -> Think IRE As Hospital Reception Desk 

                -> Patient Walks In (Discovery Finds A Device)

                    -> Receptionist Asks: "Have You Been Here Before ?"

                        Patient Says "YES" -> Pull Existing File, Update It (Reconciliation)

                        Patient Says "NO" -> Create A New Patient File (New CI Created)

            -> From ITOM Context 

                -> Question: What Are You ? 

                    -> Apache Web Server / Docker Container / Tomcat Server ??

                -> Question: HAve I Seen You Before ? 

                    -> Does this CI Already Exist In CMDB 

                        -> Yes : Update Existing CI 

                        -> No : Create New CI 

    
    -> Complete Flow 

        -> Discovery Scans Server 

            -> Probe Sends Question 

            -> Pattern / Sensor Collects Raw Attributes 
            (config_file, container_id, hostname etc)

            -> IRE Receives Payload 

            -> Question - 1: What Type Of CI ? 

                -> Looks At CI Identifiers List 

                -> Matches "Apache Rule" 

                -> Class = cmdb_ci_apache_web_server


            -> Question - 2: Does It Exist ? 

                ->  Ues Criterion Attributes 
                sys_class_name + config_file + version 

                -> Search cmdb_ci_apache_web_server table 

                    -> Found?: Update Existing CI 

                    -> Not Found?: Create New CI 

        -> Finally CMDB Is Updated
